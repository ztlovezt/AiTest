# Bug 记录：仓库绑定表单数据不一致

## 基本信息

- **Bug 编号**: PT-BUG-001
- **发现时间**: 2026-05-15
- **影响模块**: 精准测试 / 仓库绑定管理
- **影响页面**: `http://localhost:3000/precision-testing/repos`
- **严重级别**: HIGH

## 问题描述

在「仓库绑定」页面点击「绑定仓库」弹出表单，输入以下信息后点击保存：

| 表单字段 | 输入值 |
|---------|-------|
| 仓库名称 | TestNova |
| 仓库地址 | https://github.com/ztlovezt/TestNova |
| 分支 | main |
| 本地路径 | E:\testhub_platform |

**预期结果**：列表中新增一行，显示刚输入的仓库信息。

**实际结果**：列表新增了一行，但显示的内容与输入完全不符（字段为空或显示默认值）。

## 根因分析（第一轮排查）

### 1. 前端表单字段 vs 后端模型字段不匹配

| 前端字段名 | 后端模型字段 | 序列化器支持 | 问题 |
|-----------|-------------|-------------|------|
| `name` | 无直接字段（FK 到 `project.name`） | ❌ 未暴露 | 前端提交的 `name` 被丢弃 |
| `repo_url` | `repo_url` | ❌ 未暴露 | 字段存在但 serializer 未处理 |
| `branch` | `default_branch` | ❌ 未暴露 | 字段名不同，序列化器未映射 |
| `local_path` | `repo_path` | ❌ 未暴露 | 字段名不同，序列化器未映射 |

### 2. 序列化器缺陷（修复前）

`backend/apps/precision_testing/serializers.py` 中的 `RepoBindingSerializer` 仅暴露了以下字段：

```python
class Meta:
    model = RepoBinding
    fields = ['id', 'project', 'repo_path', 'default_branch', 'is_active']
```

前端通过 API 提交的 JSON 包含 `name`、`repo_url`、`branch`、`local_path`，但 Django REST Framework 会忽略未在 `fields` 中声明的字段。

### 3. 模型字段缺失

`RepoBinding` 模型在修复前没有 `repo_url` 字段，前端提交的远程仓库地址无法存储。

## 根因分析（第二轮排查 — 真正问题）

第一轮修复后重新测试，问题仍然存在。通过直接调用序列化器验证，发现以下三个隐藏的致命问题：

### Bug A：`Meta.fields` 字段冲突导致 `repo_path` / `default_branch` 验证失败

序列化器 `Meta.fields` 同时包含了：
- `repo_path`（ModelSerializer 自动生成，因模型无 `blank=True` 而标记为 `required=True`）
- `local_path`（自定义字段，`source='repo_path'`）
- `default_branch`（ModelSerializer 自动生成，`required=True`）
- `branch`（自定义字段，`source='default_branch'`）

前端提交的数据只包含 `local_path` 和 `branch`，不包含 `repo_path` 和 `default_branch`。DRF 对 `repo_path` 自动生成 required 字段，验证时报错：

```
{'repo_path': ['此字段是必填项。']}
```

导致整个请求 400 失败，所有自定义字段都无法写入。

### Bug B：`name` 是 `SerializerMethodField`（只读）

```python
name = serializers.SerializerMethodField()
```

`SerializerMethodField` 默认 `read_only=True`，前端提交的 `name` 被直接丢弃。列表中显示的 `name` 永远是 `project.name`（如 `PrecisionDemo_1778388252`），而不是用户输入的 `TestNova`。

### Bug C：`project` 是 `OneToOneField`

一个 Project 只能绑定一个 RepoBinding。如果用户选择的 project 已被绑定，会报错：
```
{'project': ['项目 与 仓库绑定 已存在。']}
```

### Bug D：MySQL 严格模式下 `default=''` 未写入数据库层

Django 模型的 `CharField(default='')` 只在 Python ORM 层面生效，**不会**在 MySQL 表结构中创建 `DEFAULT ''` 约束。MySQL `DESCRIBE` 显示：

```
name         | varchar(200) | NO  |  | None
repo_path    | varchar(500) | NO  |  | None
```

当 `name` 为空字符串或缺失时，Django 执行 `INSERT` 不传递 `name` 值，MySQL 严格模式报错：
```
OperationalError: (1364, "Field 'name' doesn't have a default value")
```

这是导致「服务器错误，操作失败」500 报文的直接原因。

## 修复方案

### 修改 1：模型新增 `name` 字段 + 允许 `repo_path` 为空

文件：`backend/apps/precision_testing/models.py`

```python
class RepoBinding(models.Model):
    project = models.OneToOneField(
        Project, on_delete=models.CASCADE, related_name='repo_binding',
        verbose_name='关联项目'
    )
    name = models.CharField(max_length=200, blank=True, default='', verbose_name='仓库显示名称')
    repo_path = models.CharField(max_length=500, blank=True, default='', verbose_name='仓库本地路径')
    repo_url = models.CharField(max_length=500, blank=True, default='', verbose_name='仓库远程地址')
    default_branch = models.CharField(max_length=100, default='main', verbose_name='默认分支')
```

- `name`：新增独立字段，保存用户自定义的仓库显示名称
- `repo_path`：补充 `blank=True, default=''`，避免 DRF 自动生成 required 字段

### 修改 2：修复序列化器字段冲突

文件：`backend/apps/precision_testing/serializers.py`

```python
class RepoBindingSerializer(serializers.ModelSerializer):
    project_name = serializers.CharField(source='project.name', read_only=True)
    # Frontend-facing aliases
    local_path = serializers.CharField(source='repo_path', required=False, allow_blank=True)
    branch = serializers.CharField(source='default_branch', required=False, allow_blank=True)

    class Meta:
        model = RepoBinding
        fields = [
            'id', 'project', 'project_name', 'name', 'repo_url', 'repo_path',
            'local_path', 'branch', 'default_branch',
            'is_active', 'created_at', 'updated_at',
        ]
        read_only_fields = ['created_at', 'updated_at']
        extra_kwargs = {
            'name': {'required': False, 'allow_blank': True},
            'repo_url': {'required': False, 'allow_blank': True},
            'repo_path': {'required': False, 'allow_blank': True},
            'default_branch': {'required': False, 'allow_blank': True},
        }

    def validate(self, attrs: dict) -> dict:
        if self.instance is None and 'project' not in attrs:
            raise serializers.ValidationError(
                {'project': 'This field is required.'}
            )
        return attrs
```

**关键修改：**
- 删除 `name = serializers.SerializerMethodField()`，改为使用模型自带的 `name` 字段（通过 `extra_kwargs` 设置为非必填）
- 保留 `local_path` 和 `branch` 作为写入别名
- 在 `extra_kwargs` 中将 `repo_path` 和 `default_branch` 显式标记为 `required=False`，消除与 `local_path`/`branch` 的字段冲突

## 根因分析（第三轮排查 — 项目下拉为空无法提交）

前两轮修复解决了「字段不匹配 / 序列化器冲突 / MySQL 默认值」问题后，用户反馈**新问题**：

> 绑定新仓库表单，**所属项目下拉选择为空**，无法提交表单新建仓库。  
> 已在项目管理 (`http://localhost:8000/admin/unified_projects/metaproject/`) 增加了新项目 **NOVA**。

### Bug E：「所属项目」下拉为空 — 两套项目模型未同步

| 层级 | 模型/接口 | 说明 |
|------|----------|------|
| 仓库绑定 `RepoBinding.project` FK | `projects.Project` | 精准测试仓库绑定的关联目标 |
| Admin 后台新建 | `unified_projects.MetaProject` | 用户实际在后台创建的项目 |
| 前端下拉请求 | `GET /api/projects/list/` → 调用 `user_projects_list` → 只查 `projects.Project` | **不会返回 MetaProject 记录** |

**根因链路**：
1. 用户在 Django Admin (`unified_projects/metaproject/`) 创建了元项目 `NOVA`
2. 前端「绑定新仓库」弹窗打开时，调用 `/api/projects/list/` 加载项目下拉
3. 该接口只查询 `projects.Project` 表，而 `MetaProject` 和 `Project` 是两张独立的表
4. `NOVA` 从未被同步到 `projects.Project`，因此下拉列表为空，用户无法选择项目，表单无法提交

## 第三轮修复方案

### 修改 5：新增统一项目同步服务

**新增文件**：`backend/apps/unified_projects/services.py`

```python
@transaction.atomic
def ensure_ai_project_for_meta_project(meta_project: MetaProject) -> Project:
    """确保元项目具备 AI 模块与对应的 projects.Project 记录。"""
    MetaProjectMember.objects.get_or_create(
        meta_project=meta_project,
        user=meta_project.owner,
        defaults={'role': 'owner'},
    )
    ProjectModule.objects.get_or_create(
        meta_project=meta_project,
        module_type='AI',
        defaults={'config': {}},
    )
    # 查找或创建对应的 Project 记录，并同步 name/description/status/owner
    project = Project.objects.filter(unified_meta_project=meta_project).first()
    if project:
        # ... 同步更新已有记录 ...
        return project
    return Project.objects.create(
        name=meta_project.name,
        description=meta_project.description,
        status=meta_project.status,
        owner=meta_project.owner,
        unified_meta_project=meta_project,
    )
```

**职责**：
- 为每个 `MetaProject` 自动创建对应的 `Project` 记录（通过 `unified_meta_project` 外键关联）
- 同时补齐 `MetaProjectMember`(owner 角色) 和 `ProjectModule`(AI 模块)
- 幂等设计：已存在则同步更新字段差异，避免重复创建

### 修改 6：项目下拉接口自动补齐元项目

**修改文件**：`backend/apps/projects/project_list_views.py` → `user_projects_list()`

```python
@api_view(['GET'])
@permission_classes([IsAuthenticated])
def user_projects_list(request):
    user = request.user
    accessible_meta_projects = MetaProject.objects.filter(
        models.Q(owner=user) | models.Q(members__user=user)
    ).select_related('owner').distinct()

    for meta_project in accessible_meta_projects:
        ensure_ai_project_for_meta_project(meta_project)

    projects = Project.objects.filter(
        models.Q(owner=user)
        | models.Q(members=user)
        | models.Q(unified_meta_project__in=accessible_meta_projects)
    ).distinct().values('id', 'name', 'status').order_by('name')
    return Response({'results': list(projects)})
```

**关键变更**：
- 接口读取时自动遍历用户可访问的 `MetaProject`，调用 `ensure_ai_project_for_meta_project` 补齐
- 查询条件增加 `Q(unified_meta_project__in=accessible_meta_projects)`，确保同步后的 Project 出现在结果中
- **效果**：只要用户能访问某个 MetaProject（如 admin 创建的 NOVA），下拉列表就能看到它

### 修改 7：Admin 保存即时同步

**修改文件**：`backend/apps/unified_projects/admin.py` → `MetaProjectAdmin`

```python
class MetaProjectAdmin(admin.ModelAdmin):
```

## 经验教训

1. **前后端字段对齐**：新增表单功能时，应同步确认后端序列化器是否正确映射了所有前端字段。
2. **DRF ModelSerializer 字段冲突**：当 `Meta.fields` 同时包含模型原始字段名和自定义 `source` 别名时，ModelSerializer 会自动为原始字段生成 `required=True` 的字段，导致验证失败。应使用 `extra_kwargs` 显式设置 `required=False`，或从 `fields` 中移除原始字段名。
3. **SerializerMethodField 是只读的**：`SerializerMethodField` 默认 `read_only=True`，不能用于接收前端输入。如需支持用户自定义名称，应在模型中新增独立字段，而非依赖 `SerializerMethodField`。
4. **Django `default` ≠ MySQL `DEFAULT`**：`CharField(default='')` 只在 Python ORM 层面生效，不会在 MySQL 表结构中创建 `DEFAULT ''` 约束。在 MySQL 严格模式下，这会导致 `Field doesn't have a default value` 的 500 错误。生产环境应通过 `RunSQL` 迁移或手动 `ALTER TABLE` 补充数据库层默认值。
5. **直接测试序列化器**：Bug 表面现象是「显示不对」，但真正原因是「保存失败」。通过直接调用 `Serializer(data=...).is_valid()` 可以快速定位验证层面的问题，比端到端调试效率高得多。
6. **测试覆盖**：应在集成测试中覆盖「表单提交 → API 响应 → 列表渲染」的完整链路，避免字段丢失未被发现。
7. **多模型项目架构的同步陷阱**：当系统存在两套项目模型（如 `MetaProject` 统一项目 vs `Project` 业务项目）时，**任何一处创建/修改入口都必须考虑同步**。Admin 后台、API 接口、数据迁移脚本都是独立的写入路径，遗漏任一都会导致「下拉为空」「找不到关联」等问题。最佳实践是抽取统一的同步服务（如 `ensure_ai_project_for_meta_project`），并在所有写入点调用。
8. **双保险同步策略**：「Admin 保存时即时同步」（修改 7）+ 「下拉读取时兜底补齐」（修改 6）的组合能覆盖历史数据和并发场景，避免因某条链路遗漏导致用户侧功能不可用。

## 根因分析（第四轮排查 — 任务队列假死 / 分析卡在 pending）

用户在仓库绑定页面点击「触发分析」，API 返回 `202 Accepted`，但随后：

- `GET /api/precision-testing/analyses/26/progress/` 轮询 650 次，状态始终为 `{"status": "pending", "progress": 0}`
- 前端分析页面持续 loading，无任何结果返回

### Bug F：Django-Q 使用 ORM Broker 导致任务从未被 worker 消费

**核心配置回顾** — `backend/settings.py` 中 `Q_CLUSTER` 配置：

```python
Q_CLUSTER = {
    'name': 'testhub',
    'workers': 1,
    'timeout': 600,
    'retry': 1200,
    'orm': 'default',          # ← ORM Broker（问题根源）
    'redis': 'redis://127.0.0.1:6379/0',  # ← Redis 配置被忽略
    'sync': False,
}
```

**根因链路**：

Django-Q 的 broker 选择逻辑（`django_q/brokers/__init__.py`）：

```python
def get_broker(list_key: str = None) -> Broker:
    if Conf.BROKER_CLASS:           # 1. custom broker → 跳过
        ...
    elif Conf.IRON_MQ:              # 2. Iron MQ → 跳过
        ...
    elif isinstance(Conf.SQS, dict): # 3. AWS SQS → 跳过
        ...
    elif Conf.ORM:                  # 4. ORM (数据库队列) → **使用**
        from django_q.brokers import orm
        return orm.ORM(list_key=list_key)
    elif Conf.MONGO:                # 5. MongoDB → 跳过
        ...
    else:                           # 6. Redis → 未到达
        from django_q.brokers import redis_broker
        return redis_broker.Redis(list_key=list_key)
```

由于 `orm='default'`（非空字符串，truthy），Django-Q 选择 **ORM Broker**（数据库队列表 `django_q_ormq`）作为任务队列的存储后端，而不是配置的 Redis。

**实际情况**：

| 配置项 | 值 | 实际效果 |
|-------|-----|---------|

## 经验教训（第四轮）

1. **Django-Q Broker 选择只看 `orm` 布尔值**：当 `orm` 为任何 truthy 值（如 `'default'`）时，Redis 配置即使存在也会被忽略。必须显式设置 `orm=False` 才能启用 Redis Broker。
2. **配置变更后必须重启进程**：Django/Q_CLUSTER 配置在进程启动时读取到内存，修改 `settings.py` 不会影响已运行的进程。调试任务队列问题时，先确认运行中的进程是否加载了最新配置。
3. **多进程环境下的调试复杂性**：同时存在多个 Django/uvicorn/qcluster 进程时，请求可能被路由到旧进程，日志和实际行为不一致。始终用 `ps aux | grep python` 确认只有预期的进程在运行。
4. **直接测试 broker 类型是排查第一步**：当任务队列不工作时，先运行 `get_broker()` 确认 broker 类型，再检查对应后端（Redis/Database）的队列状态。盲目重启进程而不确认配置会导致反复无效的调试。
5. **Django-Q ORM Broker vs Redis Broker**：
   - ORM Broker：`orm='default'` → 任务存在数据库 `django_q_ormq` 表，依赖 Django 数据库连接池，**不适合生产高并发场景**
   - Redis Broker：`orm=False` → 任务存在 Redis list，写入/读取延迟低，适合高并发。Redis 服务正常时应始终使用 Redis Broker。

## 根因分析（第六轮排查 — 触发分析 unidiff 解析崩溃）

用户在仓库绑定页面点击「触发分析」，任务创建成功但 worker 执行时崩溃：

```
Target without source: +++ "b/tests/testcase/precision_testing/Week 4/Week4_测试执行报告.md"
```

### Bug J：unidiff 解析 Git diff 时崩溃（文件名含空格/中文）

**根因链路**：

1. `analyze_code_change_task` 调用 `GitDiffAnalyzer.get_diff(base, head)`
2. `get_diff_structured` 调用 `self._repo.git.diff(unified=0, ...)` 获取 diff 文本
3. `_parse_diff_text` 调用 `PatchSet.from_string(diff_text)` 解析 diff
4. **unidiff 解析失败**：当 diff 中包含文件名带空格或中文字符的文件时（如 `Week 4/Week4_测试执行报告.md`），`unified=0` 产生的 diff 格式不兼容，unidiff 抛出 `Target without source` 异常
5. **异常未被捕获**：`_parse_diff_text` 中 `PatchSet.from_string()` 没有 try/except，异常直接上抛，任务崩溃

**为什么 `unified=0` 会出问题**：

- `unified=0` 表示 diff 中不显示上下文行，只显示变更行本身
- 对于新增/删除文件，`unified=0` 产生的 diff 头格式更紧凑，unidiff 的解析器在某些边缘情况下（引号包裹路径 + 空格 + 中文）无法正确匹配 `---` 和 `+++` 行
- 标准做法是 `unified=3`，这是 Git 和 diff 工具都兼容的格式

**为什么引号包裹路径会出问题**：

- Git diff 对含空格的文件名会自动加双引号：`+++ "b/Week 4/test.md"`
- unidiff 的 `patched_file.path` 可能包含引号（`"b/Week 4/test.md"`）
- `_normalize_path` 原来的实现没有去除引号，导致路径处理错误

**为什么 `source_file.lstrip("ab/")` 是危险的**：

```python
# 原代码
old_path = GitDiffAnalyzer._normalize_path(patched_file.source_file.lstrip("ab/"))
```

- `lstrip("ab/")` 是**字符级** strip，不是字符串前缀去除
- 例如 `source_file = "apps/foo/bar.py"`，`lstrip("ab/")` 会去掉开头的 `a` 和 `b`，结果变成 `pps/foo/bar.py`（错误！）
- 正确做法是用 `_normalize_path` 统一处理（它用 `startswith` 做前缀判断）

```python
def _resolve_function_ids(self, function_ids: list[str]) -> list[str]:
    """将可能的短名称（如 ``ASTAnalyzer.__init__``）解析为完整签名。

    策略：
    1. 已包含 ``:`` 且包含 ``.`` 的视为完整签名，直接保留。
    2. 否则在 Neo4j 中按 ``name``、``qualified_name``、``id`` 模糊匹配。
    3. 唯一匹配时替换，无匹配或多匹配时保留原值（让查询自然返回空，前端可提示）。
    """
    resolved: list[str] = []
    for fid in function_ids:
        # 简单启发：包含模块分隔符的视为完整签名
        if ":" in fid and "." in fid.split(":", 1)[0]:
            resolved.append(fid)
            continue
        # 模糊匹配
        records = self.client.execute_read(
            "MATCH (f:Function) WHERE f.name = $short "
            "OR f.qualified_name = $short "
            "OR f.id ENDS WITH $suffix "
            "RETURN f.id AS id LIMIT 5",
            {"short": fid, "suffix": f":{fid}"},
        )
        if len(records) == 1:
            resolved.append(records[0]["id"])
        elif len(records) > 1:
            logger.warning(
                "Function short name '%s' matched %d signatures, using first: %s",
                fid, len(records), records[0]["id"],
            )
            resolved.append(records[0]["id"])
        else:
            resolved.append(fid)
    return resolved
```

在 `query_impact()` 方法开头调用：

```python
def query_impact(self, changed_function_ids: list[str], ...):

    # 将短名称解析为完整签名
    changed_function_ids = self._resolve_function_ids(changed_function_ids)
    # ... 原有查询逻辑
```

#### Bug N：`buildCyElements` 不兼容后端 Cytoscape element 格式

#### 修改 23：后端 `ImpactQuery` 新增 `build_impact_graph_data` 方法

`backend/apps/precision_testing/impact_query.py`：

```python
def build_impact_graph_data(self, result: ImpactResult) -> dict[str, Any]:
    """根据 ImpactResult 构建 Cytoscape 格式的 graph data。"""
    all_function_ids = list(
        set(result.changed_functions) | set(result.impacted_functions)
    )
    all_testcase_ids = list(set(result.impacted_testcases))

    if not all_function_ids and not all_testcase_ids:
        return {"nodes": [], "edges": []}

    node_records = []
    if all_function_ids:
        func_records = self.client.execute_read(
            "MATCH (f:Function) WHERE f.id IN $ids "
            "RETURN id(f) AS internal_id, labels(f) AS labels, f AS props",
            {"ids": all_function_ids},
        )
        node_records.extend(func_records)

    if all_testcase_ids:
        tc_records = self.client.execute_read(
            "MATCH (tc:TestCase) WHERE tc.id IN $ids "
            "RETURN id(tc) AS internal_id, labels(tc) AS labels, tc AS props",
            {"ids": all_testcase_ids},
        )
        node_records.extend(tc_records)

    node_ids = [r["internal_id"] for r in node_records]

    edge_records = []
    if len(node_ids) > 1:
        edge_records = self.client.execute_read(
            "MATCH (a)-[r]->(b) "
            "WHERE id(a) IN $node_ids AND id(b) IN $node_ids "
            "RETURN id(a) AS source, id(b) AS target, type(r) AS rel_type, "
            "       properties(r) AS rel_props",
            {"node_ids": node_ids},
        )

    cy_data = _records_to_cytoscape_simple(node_records, edge_records)

    # 标记变更函数，方便前端高亮
    changed_set = set(result.changed_functions)
    for node in cy_data["nodes"]:
        if node["data"].get("node_id") in changed_set:
            node["data"]["is_changed"] = True

    return cy_data
```

#### 修改 25：前端 `buildCyElements` 兼容两种数据格式

`frontend/src/views/precision-testing/ImpactGraph.vue`：

```javascript
const buildCyElements = (nodes, edges) => {
  const elements = []
  nodes.forEach(n => {
    // 兼容后端直接返回的 Cytoscape element 格式（含 data 属性）
    if (n.data) {
      elements.push(n)
      return
    }
    // 兼容旧版扁平格式
    elements.push({
      data: {
        id: String(n.id ?? n.neo4j_id),
        label: n.name || n.id,
        type: n.labels?.[0] || n.type || 'Function',
        ...n.properties,
        ...n,
      },
    })
  })
  edges.forEach((e, idx) => {
    if (e.data) {
      elements.push(e)
      return
    }
    elements.push({
      data: {
        id: `e-${e.source}-${e.target}-${e.type}-${idx}`,
        source: String(e.source),
        target: String(e.target),
        label: e.type || e.relationship,
      },
    })
  })
  return elements
}
```

## 经验教训（第九轮）

1. **后端返回格式必须与前端期望严格对齐**：`ImpactQueryView` 返回的是业务数据结构（`ImpactResult.to_dict()`），但 `ImpactGraph.vue` 期望的是可视化数据结构（`{ nodes, edges }`）。当同一接口服务于不同消费方时，应明确区分或提供单独的 `graph_data` 字段。
2. **Cytoscape 数据格式的一致性**：项目中同时存在两种节点数据格式（扁平格式 vs Cytoscape element 格式），`buildCyElements` 必须兼容两者，否则 `GraphDataView`（全量图谱）和 `ImpactQueryView`（影响图谱）会互相冲突。
3. **短名称解析的边界情况**：`.py` 文件扩展名中的点号会触发完整签名的误判规则。启发式规则必须考虑常见文件扩展名（`.py`、`.js`、`.ts`、`.go` 等）。
4. **字段名映射要贯穿前后端**：后端 `_node_dict` 使用 `node_type` / `node_id`，前端 style 和事件处理必须使用相同的字段名，不能混用 `type` / `id`。
5. **多进程/守护进程会阻碍代码热更新**：Windows 下存在多个 uvicorn 进程监听同一端口时，请求可能被路由到旧代码进程。重启服务时必须确保所有旧进程都被终止（`taskkill //F //PID <pid>`），并验证只有一个新进程在运行。
