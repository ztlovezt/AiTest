## 一、背景与目标

### 1.1 业务背景

TestHub 当前存在的回归测试痛点：

| 痛点 | 现状 | 影响 |
|------|------|------|
| 全量回归耗时 | 单次 4 小时+ | 阻塞上线节奏，工程师等待时间长 |
| 用例-代码解耦 | 改一行代码不知道跑哪些用例 | 全跑浪费、少跑漏测 |
| 风险无量化 | 无法预判变更风险 | 高风险变更与低风险等同对待 |
| 缺陷逃逸率 | ~8% | 客户侧反馈 Bug，质量信任下降 |

### 1.2 目标拆解

参照《TestHub × TestNova 最终执行计划评审报告》Phase 1 Month 2 任务，**精准测试** 是优先级最高（🏆 极高 ROI）的模块。

| 目标 | 当前基线 | 6 个月目标 | 衡量方式 |
|------|---------|-----------|---------|
| 回归用例缩减率 | 0% | ≥ 60% | 最小回归集 / 全量用例 |
| 回归执行时间 | 4 小时 | 15 分钟 | wall-clock |
| 核心功能覆盖 | 100% | 保持 100% | 智能选集后的功能矩阵 |
| 缺陷逃逸率 | 8% | < 3% | 生产环境缺陷数 / 总缺陷数 |
| 变更影响识别准确率 | — | ≥ 85% | 影响函数正确数 / 实际相关函数数 |
| Coverage 数据新鲜度 | — | ≥ 95% | 变更分析时 coverage 状态为 fresh 的比例 |

### 1.3 范围边界

**纳入范围（V1）**：
- 后端 Python 代码变更检测（Django + DRF）
- API 层用例-代码关联（pytest 自动化）
- Git 仓库绑定与 commit diff 分析
- 最小回归集生成与执行

**暂不纳入**（后续迭代）：
- 前端 Vue 代码变更检测（Phase 2）
- UI 自动化用例关联（Phase 2）
- 生产 RUM 数据闭环（Phase 3）
- GraphRAG 缺陷预测（Phase 3）

## 二、设计原则

### 2.1 第一性原理

**回归测试的本质问题**：
> 在所有用例中，找出本次变更可能影响的最小子集，使得「执行成本最低」与「漏测概率最低」达到平衡。

**关键变量**：
1. **变更范围**（What changed）：哪些代码改了
2. **影响范围**（What's impacted）：改动会传染到哪些模块
3. **关联用例**（Which cases）：哪些用例覆盖到了这些模块
4. **风险权重**（How risky）：每个用例的失效概率

精准测试 = 上述 4 个变量的乘积 → 最小回归集

### 2.2 工程化原则

| 原则 | 落地方式 |
|------|---------|
| **不破坏现有架构** | 作为独立 Django App，复用 Django-Q2/JWT/MySQL 基础设施 |
| **降级可用** | Neo4j 不可用时回退启发式规则；XGBoost 未训练时用规则评分 |
| **可灰度** | 通过 `PRECISION_TESTING.enabled` 开关控制；项目级独立绑定 |
| **数据可解释** | 每条预测结果记录特征向量与模型版本 |
| **混合启动策略** | 手工标注 → 静态分析 → 动态学习，三阶段递进 |

## 五、数据模型设计

### 5.1 MySQL 主表（6 张）

```
RepoBinding (仓库绑定)
    ↓ 1:N
CodeChangeAnalysis (代码变更分析)
    ↓ 1:N
ImpactAnalysis (影响分析)
    ├── 1:N → RiskPredictionRecord (风险预测)
    └── 1:N → PrecisionRunRecord (精准回归执行) ──→ TestPlan (现有表)

TestCase (现有表) ──┐
                   ├── 1:N → TestCaseCodeMapping (用例代码映射)
                   └── 1:N → RiskPredictionRecord (风险预测)
```

| 表名 | 关键字段 | 用途 |
|------|---------|------|
| `precision_repo_bindings` | `project_id`, `repo_path`, `default_branch` | 项目↔Git 仓库 1:1 绑定 |
| `precision_change_analyses` | `base_commit`, `head_commit`, `changed_files`(JSON), `changed_functions`(JSON) | 单次 commit diff 分析记录 |
| `precision_testcase_mappings` | `testcase_id`, `function_signature`, `mapping_type`, `confidence` | 用例与函数的关联（手工/静态/动态三种来源） |
| `precision_impact_analyses` | `impacted_functions`(JSON), `impacted_testcases`(JSON), `min_regression_set`(JSON) | 一次变更对应的影响范围与最小回归集 |
| `precision_risk_predictions` | `testcase_id`, `risk_score`, `risk_level`, `features`(JSON), `model_version` | 单条用例的失效概率预测（特征+分数+等级） |
| `precision_run_records` | `selected_testcases`(JSON), `total_testcases`, `reduction_rate`, `run_plan_id` | 精准回归执行记录（含缩减率） |

### 5.2 Neo4j 图谱模型

**节点（Node）**：
- `(:Project {id, name})` — 项目
- `(:Module {path, app})` — Django App / 文件
- `(:Class {name, signature})` — 类定义
- `(:Function {signature, name, file_path, lines})` — 函数定义
- `(:TestCase {id, title, priority})` — 测试用例
- `(:APIEndpoint {path, method, view})` — REST API 端点

**关系（Relationship）**：
- `(:Module)-[:CONTAINS]->(:Class)` — 模块包含类
- `(:Class)-[:HAS_METHOD]->(:Function)` — 类拥有方法
- `(:Module)-[:CONTAINS]->(:Function)` — 模块包含函数（非类方法）
- `(:Function)-[:CALLS {weight}]->(:Function)` — 调用关系（权重=调用次数）
- `(:APIEndpoint)-[:DISPATCHES_TO]->(:Function)` — DRF 路由→视图函数
- `(:TestCase)-[:COVERS {confidence, source}]->(:Function)` — 用例覆盖函数（手工/静态/动态）
- `(:TestCase)-[:TESTS]->(:APIEndpoint)` — API 用例测试端点

**索引与约束**（`cypher/schema.cypher`）：
```cypher
CREATE CONSTRAINT function_signature_unique IF NOT EXISTS
  FOR (f:Function) REQUIRE f.signature IS UNIQUE;
CREATE CONSTRAINT testcase_id_unique IF NOT EXISTS
  FOR (t:TestCase) REQUIRE t.id IS UNIQUE;
CREATE INDEX function_file_path IF NOT EXISTS FOR (f:Function) ON (f.file_path);
CREATE INDEX testcase_priority IF NOT EXISTS FOR (t:TestCase) ON (t.priority);
```

## 六、关联图谱三阶段构建策略

### 6.1 战略意图

> 单一手段的关联图谱要么准确率不足（纯静态），要么冷启动困难（纯手工），要么数据不够（纯动态）。**混合策略** 通过三阶段递进，让每个阶段的产出为下一阶段做信任背书。

```
Phase 1: 手工打标核心用例
  目标: 80 条 P0 用例 100% 关联，覆盖率 30%
  特点: 准确率 100%，建立信任锚点
       ↓
Phase 2: 静态分析自动扩展
  目标: 覆盖率从 30% → 70%
  特点: Coverage.py + AST + DRF 路由解析
       ↓
Phase 3: 动态学习持续优化
  目标: 准确率 ≥ 85%，覆盖率 ≥ 90%
  特点: 历史运行数据 + 失败传播分析
```

### 6.2 Phase 1：手工打标（Week 1-2）

**做什么**：
- 由资深 QA 在前端「用例映射管理」页面手工标注 P0 核心用例与代码函数的关联
- 每个项目至少标注 80 条核心用例（覆盖登录/注册/创建项目/CRUD 主流程）
- 标注数据写入 `TestCaseCodeMapping`，`mapping_type='manual'`，`confidence=1.0`

**为什么有效**：
- 资深 QA 对核心业务最熟悉，准确率 100%
- 这批"金标准"数据将作为后续静态/动态结果的对照基准
- 覆盖了 80% 的回归流量（Pareto 法则）

**交付指标**：
| 指标 | 目标 |
|------|------|
| P0 用例标注完成率 | 100% |
| 关联函数数量 | ≥ 200 个 |
| 平均每条用例关联函数数 | 2-5 个 |

### 6.3 Phase 2：静态分析（Week 3-4）

**技术路径**：

```
pytest 用例执行（带 coverage）
    ↓
.coverage 文件解析（coverage.py JSON 报告）
    ↓
解析每条用例覆盖到的源文件 + 行号
    ↓
通过 AST 反查行号 → 函数签名
    ↓
写入 TestCaseCodeMapping (mapping_type='auto_static')
```

**额外补充：DRF 路由静态解析**：
- 通过 `astroid` 解析 `urls.py` + `views.py`
- 识别 `path('api/xxx/', XxxView.as_view())` → `XxxView.method` 映射
- 在 Neo4j 中建立 `(:APIEndpoint)-[:DISPATCHES_TO]->(:Function)` 关系
- API 测试用例通过 URL 模板自动关联到视图函数

**降级策略**：
- coverage.py 无法运行（环境问题）→ 仅用 AST + 路由静态解析
- 函数签名匹配失败 → 标记 `confidence=0.5`，进入人工 review 队列

**交付指标**：
| 指标 | 目标 |
|------|------|
| 自动关联用例数 | 现有用例的 70% |
| 平均关联置信度 | ≥ 0.8 |
| 与 Phase 1 标注重合度 | ≥ 90%（验证准确率） |

### 6.4 Phase 3：动态学习（Week 5-6）

**做什么**：
- 收集历史 N 个月的执行记录（`TestRunCase` + 失败堆栈）
- 用机器学习方法学习"代码改动 → 用例失败"的潜在关联
- 生成置信度较低但覆盖更广的关联（mapping_type='auto_dynamic'）

**关键算法**：

1. **失败传播图谱**：
   - 当用例 T1 失败，分析此次涉及的代码变更
   - 若 T1 的失败堆栈指向函数 F1，建立 `T1 -[COVERS {confidence=0.6, source='dynamic'}]-> F1`
   - 多次失败后置信度逐步提升（贝叶斯更新）

2. **共现分析**：
   - 同一 commit 中改动的函数 + 该 commit 后失败的用例 → 弱关联
   - 排除噪声：用例改动本身、测试数据问题

3. **特征学习（XGBoost 风险预测的训练数据来源）**：
   - 输入特征：函数复杂度、变更频率、历史失败率、调用深度
   - 输出标签：用例是否失败（来自 TestRunCase 历史）

**交付指标**：
| 指标 | 目标 |
|------|------|
| 动态关联补充覆盖率 | 总覆盖率从 70% → 90% |
| 模型 AUC | ≥ 0.85 |
| 运行 30 天后准确率提升 | 相对静态分析 +5% |

## 七、核心算法与流程

### 7.1 端到端流程图

```
┌──────────────────────────────────────────────────────────────────┐
│ 触发源                                                            │
│  ① Git push (Webhook)  ② 手动触发  ③ CI/CD 流水线                │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ Step 1: 代码变更检测 (GitAnalyzer)                                │
│  • git diff base..head                                            │
│  • 解析变更文件 + 变更行号 (unidiff)                              │
│  • 输出: changed_files[], changed_line_ranges[]                  │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ Step 2: AST 解析定位函数 (ASTAnalyzer)                            │
│  • 解析每个变更文件 (ast.parse)                                   │
│  • 行号 → 函数签名映射                                            │
│  • 输出: changed_functions[] (apps.users.views:LoginView.post)   │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ Step 3: 影响传播分析 (Neo4j Cypher Query)                         │
│  MATCH (f:Function) WHERE f.signature IN $changed_functions      │
│  CALL apoc.path.subgraphNodes(f, {                               │
│    relationshipFilter: '<CALLS', maxLevel: 3                     │
│  }) YIELD node                                                    │
│  • 输出: impacted_functions[] (含传播深度 + 权重)                │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ Step 4: 用例反查 (Neo4j 二次查询)                                 │
│  MATCH (t:TestCase)-[r:COVERS]->(f:Function)                     │
│  WHERE f.signature IN $impacted_functions                        │
│  • 输出: candidate_testcases[] + 关联置信度                      │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ Step 5: 风险评分 (RiskPredictor)                                  │
│  特征工程:                                                         │
│    • 变更函数复杂度 (cyclomatic complexity)                       │
│    • 用例历史失败率                                                │
│    • 关联置信度                                                    │
│    • 代码作者经验                                                  │
│    • 调用深度                                                      │
│  XGBoost / 启发式 → risk_score (0.0 ~ 1.0)                       │

│    • 可选: P1 + 风险分 0.4-0.7 (按时间预算选)                     │
```

### 7.2 关键 Cypher 查询

**查询 1：找出受变更影响的所有函数（含 3 层传播）**
```cypher
MATCH (changed:Function)
WHERE changed.signature IN $changed_signatures
WITH changed
CALL apoc.path.subgraphNodes(changed, {
  relationshipFilter: '<CALLS',
  maxLevel: 3
}) YIELD node
RETURN DISTINCT node.signature AS signature,
       node.file_path AS file_path
```

**查询 2：通过受影响函数反查所有相关用例**
```cypher
MATCH (t:TestCase)-[r:COVERS]->(f:Function)
WHERE f.signature IN $impacted_signatures
RETURN t.id AS testcase_id,
       t.priority AS priority,
       MAX(r.confidence) AS max_confidence,
       COUNT(f) AS coverage_count
ORDER BY priority ASC, max_confidence DESC
```

**查询 3：API 端点变更时的关联用例**
```cypher
MATCH (api:APIEndpoint)-[:DISPATCHES_TO]->(f:Function)
WHERE f.signature IN $changed_signatures
WITH api
MATCH (t:TestCase)-[:TESTS]->(api)
RETURN DISTINCT t.id AS testcase_id, api.path AS api_path
```

### 7.3 风险评分公式

**启发式版本（无训练数据时）**：
```
risk_score = 0.4 * coverage_confidence
           + 0.3 * change_intensity
           + 0.2 * historical_failure_rate
           + 0.1 * priority_weight

其中:
  coverage_confidence  = 关联置信度 (0~1)
  change_intensity     = 变更行数 / 函数总行数
  historical_failure_rate = 该用例近 30 天失败次数 / 执行次数
  priority_weight      = {P0: 1.0, P1: 0.7, P2: 0.4, P3: 0.2}
```

**XGBoost 版本（有训练数据后）**：
- 特征向量：上述 4 项 + 函数圈复杂度 + 调用深度 + 作者变更频次
- 标签：该用例在该次 commit 后是否失败（0/1）
- 训练数据：`TestRunCase` 历史 ≥ 1000 条
- 模型评估：5-fold CV，AUC ≥ 0.85 才上线

### 7.4 最小回归集算法

```python
def select_minimum_regression_set(
    scored_testcases: List[Tuple[int, float, str]],
    time_budget_seconds: int = 900,  # 默认 15 分钟
) -> List[int]:
    """
    输入: [(testcase_id, risk_score, priority), ...]
    输出: 选中的 testcase_id 列表
    """
    # 1) 必选层: P0 全部 + 风险 > 0.7
    must_run = [tc for tc, score, prio in scored_testcases
                if prio == 'P0' or score > 0.7]

    # 2) 可选层: P1 + 风险 0.4-0.7, 按风险降序
    candidates = sorted(
        [(tc, score) for tc, score, prio in scored_testcases
         if prio == 'P1' and 0.4 <= score <= 0.7],
        key=lambda x: -x[1]
    )

    # 3) 时间预算贪心选择
    selected = list(must_run)
    estimated_time = sum_estimated_time(selected)
    for tc, score in candidates:
        tc_time = get_avg_runtime(tc)
        if estimated_time + tc_time <= time_budget_seconds:
            selected.append(tc)
            estimated_time += tc_time

    return selected
```

**最小回归集贪心选择伪码**：

```python
def select_minimum_regression_set(
    impact: ImpactAnalysis,
    predictions: list[RiskPredictionRecord],
    time_budget_s: int = 900,
    force_full: bool = False,
) -> tuple[list[int], float, int]:
    """返回 (selected_ids, reduction_rate, estimated_seconds)。"""
    if force_full:
        all_ids = list(TestCase.objects.filter(project=...).values_list("id", flat=True))
        return all_ids, 0.0, estimate_time(all_ids)

    # 1) 必选层：P0 全部 + 风险 ≥ 0.7
    must_run = {p.testcase_id for p in predictions
                if p.testcase.priority == "critical" or p.risk_score >= 0.7}

    # 2) 候选层：P1 + 0.4 ≤ 风险 < 0.7，按风险降序
    candidates = sorted(
        [p for p in predictions
         if p.testcase.priority in ("high",) and 0.4 <= p.risk_score < 0.7],
        key=lambda p: -p.risk_score,
    )

    # 3) 时间预算贪心选择
    selected = list(must_run)
    used_time = sum(estimator.estimate(tid) for tid in selected)
    for p in candidates:
        cost = estimator.estimate(p.testcase_id)
        if used_time + cost <= time_budget_s:
            selected.append(p.testcase_id)
            used_time += cost

    total = TestCase.objects.filter(project=...).count()
    reduction = round(1.0 - len(selected) / max(total, 1), 3)
    return selected, reduction, used_time
```

#### 8.5.4 关键技术挑战与应对

**定位**：解决用户"不知道 .coverage 是否存在、是否过期"的痛点，在保持手动流程的前提下提供状态可见性与过期预警。

**设计原则**：只读、提示、不自动执行 —— 前端不直接调用 `pytest`，仅展示状态并引导用户手动操作。

**状态判定规则（后端 `CoverageStatusView` 实现）**：

| 状态 | 判定条件 | 前端展示 |
|------|---------|---------|
| `fresh`（最新） | `.coverage` 存在，且 mtime >= HEAD commit time，且工作区无未提交修改 | 绿色标签 + "Coverage 数据最新" |
| `outdated`（过期） | `.coverage` 存在，但 mtime < HEAD commit time，或工作区有未提交修改 | 黄色标签 + "Coverage 可能过期，建议重新运行测试" |
| `missing`（缺失） | `.coverage` 不存在 | 红色标签 + "未找到 Coverage 数据，请先运行测试" |

```
└─────────────────────────────────────────────────────────────────────┘
```

**变更分析前的自动检测（ChangeAnalyses.vue）**：

### 8.10 视觉回归测试专项计划（横跨 Week 5-8）

**目标**：解决 ECharts canvas、Element Plus 动态组件、复杂布局等场景下传统 DOM 断言无法验证视觉正确性的问题，建立像素级可重复的界面质量门禁。

#### 8.10.1 问题背景与必要性

| 场景 | 传统 E2E 局限 | 视觉回归能力 |
|------|--------------|-------------|
| ECharts 饼图/折线图/条形图 | 只能断言 `canvas` 存在，无法验证扇区数量、数据点位置、颜色正确性 | screenshot diff 可捕获渲染异常（缺失扇区、颜色错乱、数据截断） |
| Element Plus 表格/分页/下拉 | DOM 结构稳定但样式可能错位（列宽溢出、分页按钮重叠） | 像素级对比可发现 1px 级错位 |
| 响应式布局（resize） | 只能断言元素存在，无法验证断点切换后的排版正确性 | 多分辨率截图对比 |
| 主题切换（dark/light） | DOM 相同但 CSS 变量不同，传统测试无法覆盖 | 截图对比直接捕获主题色异常 |
| 空数据 / 加载态 / 错误态 | 空状态和正常状态 DOM 结构可能相同，仅靠 class 难以区分 | 截图可明确区分 skeleton、空状态、真实数据 |

#### 8.10.2 技术选型

| 维度 | 方案 | 选型理由 |
|------|------|---------|
| 核心引擎 | Playwright `page.screenshot()` + `toMatchSnapshot()` | 与现有 E2E 框架统一，无需引入第二套工具 |
| 快照管理 | Git LFS 或 CI artifact 存储 | 基线快照随代码版本管理，PR diff 直接可见 |
| 差异阈值 | `threshold: 0.2`（默认）+ `maxDiffPixels: 50` | 允许字体抗锯齿等噪声，阻断实质性渲染异常 |
| 多分辨率 | `[1920x1080, 1440x900, 1024x768, 768x1024, 375x667]` | 覆盖桌面、平板、手机三端 |
| 浏览器矩阵 | Chromium + WebKit | WebKit 可捕获 Safari 特有的渲染差异 |
| 不稳定区域掩码 | `mask: [page.locator('.el-loading-mask'), page.locator('.echarts-tooltip')]` | loading 动画、tooltip 等动态内容不参与对比 |

## 十二、运维部署：服务启动体系与问题排查实录

> 本章记录 2026-05-15 至 2026-05-16 期间，仓库绑定与触发分析功能在联调测试中暴露的全部问题、根因分析与根治方案。这些问题属于**开发环境运维**范畴，不涉及业务算法，但对开发效率影响极大，故单独成章以供后续参考。

### 12.1 服务启动体系总览

#### 12.1.1 脚本分层设计

| 脚本 | 作用域 | 操作对象 | 权限要求 |
|------|--------|---------|---------|
| `scripts/启动基础设施.bat` | 系统级 | Redis + MySQL + Neo4j Windows 服务 | **管理员** |
| `scripts/停止基础设施.bat` | 系统级 | Redis + MySQL + Neo4j Windows 服务 | **管理员** |
| `scripts/启动所有服务.bat` | 项目级 | Django + Django-Q2 + Vite 前端 | 普通用户 |
| `scripts/停止所有服务.bat` | 项目级 | Django + Django-Q2 + Vite 前端 | 普通用户 |

**日常开发流程**：
1. **开机/启动开发环境**：`启动基础设施.bat`（管理员）→ `启动所有服务.bat`
2. **发版/Bug 修复后重启**：`停止所有服务.bat` → `启动所有服务.bat`
3. **关机/结束工作**：`停止所有服务.bat` → `停止基础设施.bat`（管理员）

#### 12.1.2 职责分离原则

| 脚本 | 职责 | 禁止行为 |
|------|------|---------|
| `启动所有服务.bat` | 检查端口 → 启动子进程 → 保持运行 | **禁止** 清理残留进程 |
| `停止所有服务.bat` | 按 PID 文件精准停止 → 端口扫描兜底 → 进程名 fallback 清理 | **禁止** 启动任何服务 |

启动脚本清理残留进程是**职责错位**，会导致自杀风险（见 12.3.6 轮）。

---

### 12.2 问题排查实录（六轮）

#### 12.2.1 第一轮：前后端字段不匹配

**现象**：绑定新仓库后，列表页显示的不是用户提交的数据。

**根因**：前端提交字段名与后端模型字段名不一致：

| 前端提交字段 | 后端模型字段 | 状态 |
|------------|------------|------|
| `name` | `name`（新增） | 未映射 |
| `repo_url` | `repo_url`（新增） | 未映射 |
| `branch` | `default_branch` | 不一致 |
| `local_path` | `repo_path` | 不一致 |

**修复**：
1. `models.py` 新增 `name`、`repo_url` 字段，并添加 `DEFAULT ''`
2. `serializers.py` 新增对应字段的映射
3. 创建并执行迁移文件

---

#### 12.2.2 第二轮：序列化器字段冲突 + 默认值缺失

**现象**：保存表单后 500 错误；数据库中已有记录的 `name`/`repo_path` 为空字符串。

**根因**：
1. `SerializerMethodField` 生成的 `project_name` 与模型字段 `name` 冲突，`name` 被设为只读
2. `CharField` 未设置 `default=''`，已有记录回填空字符串
3. `local_path` 被映射为 `SerializerMethodField` 而非模型字段

**修复**：
1. 将 `project_name` 重命名为 `project_name_display`，解除对 `name` 字段的占用
2. `CharField` 全部添加 `default=''`
3. `local_path` 正确映射到 `repo_path`

---

#### 12.2.3 第三轮：MetaProject/Project 双模型未同步

**现象**：仓库绑定表单中"所属项目"下拉框为空，无可选数据。

**根因**：
1. 前端调用 `/api/projects/list/`，后端 `user_projects_list` 视图返回 0 条记录
2. 系统使用 `Project`（业务模型）和 `UnifiedMetaProject`（元模型）双模型，admin 用户不是任何 Project 的 owner/member
3. 所有 Project 的 `unified_meta_project` 外键为空，无法通过 `unified_meta_project__in=accessible_meta_projects` 匹配

**修复**：
```python
# backend/apps/projects/project_list_views.py
if user.is_superuser:
    projects = Project.objects.all().values('id', 'name', 'status').order_by('name')
else:
    projects = Project.objects.filter(
        models.Q(owner=user) | models.Q(members=user) |
        models.Q(unified_meta_project__in=accessible_meta_projects)
    ).distinct().values('id', 'name', 'status').order_by('name')
```

---

#### 12.2.4 第四轮：Django-Q ORM Broker 配置陷阱 + 多 Python 进程冲突

**现象**：触发分析后任务一直卡在 `pending`，`progress` 始终为 0，前端轮询 650 次无结果。

**根因（两层）**：

**层 1：ORM Broker 配置陷阱**

Django-Q 的 `Q_CLUSTER` 配置中，`orm='default'` 会强制使用 ORM Broker（数据库队列表），Redis 配置被完全忽略。Worker 初始化时用 Redis，数据库里的任务永远不会被消费。

| 配置项 | 问题值 | 正确值 |
|--------|--------|--------|
| `orm` | `'default'`（truthy，强制 ORM Broker） | `False` 或完全省略 |
| `redis` | `redis://127.0.0.1:6379/0` | 同左（但需确保 Redis 可访问） |

**层 2：多 Python 进程冲突**

Windows 上多个 `python manage.py runserver` 和 `python manage.py qcluster` 实例同时运行，请求被随机路由到旧代码实例，修复不生效。

**修复**：
1. `settings.py` 中移除 `Q_CLUSTER['orm']` 键（或设为 `False`）
2. `settings.py` 添加运行时断言：启动时验证 `get_broker()` 返回 `Redis` 类型，否则 `RuntimeError`
3. `start_all.py` 采用 PID 文件精准管理：启动时写入 PID，停止时按 PID 精准 kill
4. 启动脚本添加 `verify_redis_enqueue()`：启动后实际向队列写入健康检查任务验证

---

#### 12.2.5 第五轮：Bat 编码与复杂逻辑导致命令解析错误

**现象**：`停止所有服务.bat` 执行时出现 `'ct:'`、`'PID'`、`'浣宠敤'` 等乱码命令错误。

**根因**：
1. `chcp 65001`（UTF-8 代码页）后，`for` 循环解析 `tasklist` CSV 输出时，UTF-8 字节流被拆分成独立的乱码命令执行
2. `wmic` 在 Windows 11 已弃用，CSV 解析不可靠
3. bat 脚本自身实现了停止逻辑，又调用 `start_all.py --stop`，两套逻辑互相干扰

**修复**：
1. 重写 `停止所有服务.bat`：移除 `chcp 65001`、`title`、`setlocal`，纯 ASCII 内容
2. 简化逻辑：只做一件事——调用 `start_all.py --stop`
3. `wmic /FORMAT:CSV` 替换为 `tasklist /FO CSV`
4. 解析逻辑从 `split(",")` 改为 `split('","')` + `strip('"')`

---

#### 12.2.6 第六轮：启动脚本自杀 bug

**现象**：`启动所有服务.bat` 执行到 `清理残留 Python 进程...` 后窗口直接关闭，显示 `[WARN] Python script returned error`。

**根因**：`start_backend()` 调用 `cleanup_all_python_processes()`，该函数通过 `tasklist` 扫描所有 `python.exe` 进程，但**没有跳过 `start_all.py` 自己的 PID**，导致脚本自杀。

**修复**：
1. `cleanup_all_python_processes()` 中添加 `self_pid = os.getpid()`，kill 前检查 `pid != self_pid`
2. `stop_all()` 中同样添加 `self_pid` 跳过（已在前序修复中完成）
3. **最终方案**：启动脚本**彻底移除**进程清理逻辑，改为纯端口检查。清理职责完全交给 `停止所有服务.bat`。

---

### 12.3 四层根治方案

| 层级 | 措施 | 实施位置 | 效果 |
|------|------|---------|------|
| **配置层** | 运行时断言：启动时强制验证 Broker 类型 | `backend/settings.py` | 配置错误时服务无法启动 |
| **进程管理层** | PID 文件精准管理 + 启动前强制清理 | `scripts/start_all.py` | 杜绝多进程冲突 |
| **启动校验层** | Broker 类型验证 + Redis 队列写入验证 | `scripts/start_all.py` | 启动即知配置是否正确 |
| **职责分离层** | 启动脚本不清理进程，停止脚本不启动服务 | 四个 bat 脚本 | 消除自杀风险 |

### 12.4 快速诊断手册

| 症状 | 可能原因 | 诊断命令 | 修复动作 |
|------|---------|---------|---------|
| 绑定仓库后显示空白数据 | 前后端字段不匹配 | 检查 serializer `name`/`repo_url` 是否只读 | 解除字段冲突，重命名 `project_name_display` |
| 表单保存 500 错误 | `CharField` 无默认值 | `python manage.py migrate --check` | 添加 `default=''` |
| "所属项目"下拉为空 | admin 无权查看 Project | `curl /api/projects/list/` | `user_projects_list` 添加 superuser 分支 |
| 分析任务永远 `pending` | Django-Q 使用 ORM Broker | `python -c "from django_q.brokers import get_broker; print(type(get_broker()))"` | 移除 `Q_CLUSTER['orm']` |
| 修复后仍不生效 | 多个 Python 进程冲突 | `tasklist /FI "IMAGENAME eq python.exe"` | `停止所有服务.bat` 彻底清理后重试 |
| bat 出现乱码命令 | `chcp 65001` + `for` 循环 | 直接观察 | 重写 bat，移除 `chcp 65001`，纯 ASCII |
| 启动脚本闪退 | 自杀 bug 或进程清理异常 | 观察输出停在哪一步 | 移除启动脚本中的进程清理逻辑 |
